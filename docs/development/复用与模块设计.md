# 复用、抽象与模块设计

## 1. 已有实现优先

新增能力前，必须搜索同类函数、调用方和测试，并确认实际行为。搜索不能只匹配拟定的新函数名，还要覆盖输入输出、业务关键词和底层操作。

按以下顺序选择实现方式：

1. 已有实现满足需求：直接调用。
2. 已有实现主体适用：在原实现上做必要扩展，并验证已有调用行为。
3. 多处存在相同规则：将规则归入合适的现有模块，迁移相关调用方到同一实现。
4. 确实存在不同契约：说明输入、输出、副作用或生命周期差异，再建立独立实现。

**禁止已有逻辑却重新实现一套相似逻辑**，包括改名复制、局部复制后修改少量条件、在 UI 与后台各自计算同一个业务规则，以及新增包装后在包装内部重写算法。

现有实现有缺陷时优先修复原实现。若受兼容性或范围约束暂时无法迁移，应明确差异、调用范围和迁移条件，不能把重复实现永久藏在 `v2`、`new`、`legacy` 后面。

新增内容时同步检查它是否已经取代旧内容。在本次范围内完成相关替换和失效逻辑清理，不让新入口、新开关和旧版本持续并存；有真实兼容性要求时保留必要部分，不顺手扩大清理范围。

## 2. 复用语义，不强行合并形状

- 同一业务规则必须由同一处负责，不能因为调用位置不同而复制。
- 仅仅长得相似的代码不一定共享语义。不同规则若会独立变化，可以分别表达；禁止通过一串模式开关将它们硬塞进通用函数。
- 不为统一外观而统一实现。两三个清晰分支可以直接表达，不必改成注册表、策略类或通用执行框架；同一业务规则仍须复用。
- 新共享函数必须有明确职责。不要把领域规则随意塞进 `utils.py`、`common.py` 或万能管理类。
- 函数应显式接收真正需要的数据，避免只为获得一个字段而传入整个窗口、上下文或全局配置对象。

## 3. 抽象必须减少复杂性

建立抽象前，应能具体说明它消除了哪一处重复规则、隔离了哪一个外部边界，或管理了哪一类资源。不接受仅凭“便于扩展”建立接口、工厂、注册器和多层服务。

先消除问题，再考虑封装问题。如果调整已有流程就能消除特殊分支，应直接调整，不为该分支另套策略、适配器或配置。

优先减少需要理解的概念，而非代码行数。三个清晰分支可能比映射表、回调和分发器的组合更简单；不能以代码更短作为新增抽象的依据。

禁止以下模式：

- `UI → manager → service → helper → 原函数`，中间层只做同参数转发。
- 用多层嵌套函数、回调或闭包包装本可顺序执行的流程，导致读者需要反复跳转才能理解一个动作。
- 为简单状态流额外建立状态类、控制器和转移包装；一个整数状态和集中分支即可表达时，直接使用，具体见[状态与异常](状态与异常.md)。
- 为一个实现建立基类、工厂和插件注册体系，却不存在实际替换需求。
- 把一段连续逻辑拆成多个仅使用一次、职责又无法独立说明的小函数。
- 用多个布尔参数控制一个函数执行不同任务，导致调用含义难以判断。
- 为了测试方便搭建生产代码不需要的架构；应先从真实依赖边界隔离副作用。

必要的协议适配、权限检查、重试策略和资源生命周期包装可以保留，但必须确实承担这些职责。包装不能只改名，也不能掩盖失败。

审查时沿一次真实调用从入口追到实际操作：每层都应有可说明的职责。移除后既不丢失业务规则、边界契约或资源管理，也不引入重复逻辑的中间层，应当移除。不能为追求固定调用层数而合并必要边界。

## 4. 耦合应该显式且集中

- UI 负责读取输入、展示结果和触发操作；业务层负责规则；设备、文件、网络等边界负责具体读写。
- 业务计算不应依赖 UI 控件，不应通过操作界面间接获取计算参数。
- 参数在边界解析为明确的业务数据后向下传递，避免各层反复做同义字段改名、字典拆装和类型转换。
- 已有数据能直接使用时直接使用。禁止把对象拆成字典、再组装成另一个对象，最后只取少量字段；每次转换都应有实际用途，不能只是迎合新建接口。
- 不引入循环依赖。延迟导入只能解决确有需要的初始化问题，不能掩盖模块职责混乱。
- 避免隐式修改全局状态和调用方传入的对象。必要的原地修改必须体现在接口说明中。
- 一项资源或状态由一个明确主体管理；其他模块通过其接口使用，不各自维护副本。
- 不因“降低耦合”复制已有逻辑。先将共享规则放到双方可依赖的合适位置。

## 5. 配置、依赖与性能

- 不为单一固定行为增加配置层；真实配置在入口校验，内部使用统一类型和含义。
- 添加第三方依赖前，先检查标准库和项目现有依赖；说明新依赖提供的实际能力。
- 优化前确认耗时或资源瓶颈，避免无依据的缓存、并发和批处理。
- 缓存必须有明确的数据所有者、更新及失效条件。不能用新增缓存掩盖可直接消除的重复计算。
- 保持资源作用域清晰，避免导入模块时启动任务、控制设备或执行无关写入。

## 6. 快速决策表

| 遇到的情况 | 默认处理 |
| --- | --- |
| 已有函数完全满足需要 | 直接复用 |
| 只差一个真实存在的业务变化 | 在原实现处扩展，检查原调用方 |
| 一次性、无职责的转发函数 | 内联或直接调用原函数 |
| 一次性但完整的算法或资源操作 | 保留有明确意义的函数 |
| 多处使用同一业务规则 | 集中实现，调用方复用 |
| 代码相似但规则和变化来源不同 | 分别表达，不强行通用化 |
| 新抽象需要更多开关才能容纳调用方 | 重新检查是否错误合并了职责 |

状态与数据重复问题见[状态与异常](状态与异常.md)。

最终审查应问：这次修改增加了多少需要读者记住的东西，它们是否真的不可省？新增变量、函数、类、配置和转换必须降低整体理解成本，不能只是把复杂性搬到别处。
